# TEST_SPEC

Conventions and architecture decisions for the test suite. Serves as a reference to keep consistency when adding new test files.

---

## 1. Folder structure

```
tests/
├── helpers/
│   ├── index.ts              # barrel: exports setupTwoUsers, setupGroupWithTwoMembers, setupGroupWithNonMember
│   └── store-helpers.ts      # factory functions that manipulate the store
├── mocks/
│   ├── index.ts              # barrel: exports all data mocks
│   ├── balance.ts            # fixed directDebts for settlement tests
│   ├── expense.ts            # defaultEqualExpense (without id)
│   ├── global.ts             # emptyGlobal, validGlobal, validGlobalEncoded
│   ├── group.ts              # baseGroup for domain tests
│   ├── users.ts              # testAlice, testBob, testUsers
│   └── ui/
│       └── dialog.tsx        # centralized mock of @components/ui/dialog
├── setup/
│   ├── index.ts              # barrel: exports setupStoreOnly, setupStoreAndWindow
│   └── store-and-window.ts   # beforeEach helpers
└── vitest.setup.ts           # jest-dom + afterEach cleanup
```

Imports via path alias `@tests/mocks`, `@tests/setup`, `@tests/helpers`. Never import using the full internal file path — always through the barrel.

## 2. Coverage

### 2.1 Configuration (`vitest.config.ts`)

```typescript
coverage: {
    provider: "v8",
    reporter: ["text", "html"],
    include: ["src/**/*.{ts,tsx}"],
    exclude: [
        "**/node_modules/**",
        "**/dist/**",
        "public/**",
        "**/index.ts",           // barrel files — only re-export
        "**/constants.ts",       // literals with no logic
        "**/*.schema.ts",        // Zod declarations — no branches to test
        "src/main.tsx",          // entrypoint
        "src/lib/utils.ts",      // generated utility (shadcn)
        "src/components/ui/**",  // generated components (shadcn)
        "**/*.d.ts",
        "vite.config.ts",
        "vitest.config.ts",
        "tests/helpers/**/*.{ts,tsx}",
        "tests/mocks/**/*.{ts,tsx}",
        "tests/setup/**/*.{ts,tsx}",
    ],
}
```

### 2.2 Goal

100% coverage with no `/* c8 ignore */` comments. Every covered line has a test with declared intent.

### 2.3 What should not be included in coverage

| Category | Reason |
|---|---|
| `**/index.ts` | Barrel files only re-export; there is no logic |
| `**/constants.ts` | Literals with no branches |
| `**/*.schema.ts` | Zod declarations; runtime validates, there are no decision branches |
| `src/components/ui/**` | Components generated by shadcn |
| `src/lib/utils.ts` | Utility generated by shadcn |

## 3. Setup helpers

### 3.1 `setupStoreOnly()`

Resets the store with `initEmpty()`. Does not configure `window` nor `history`.

**Use in:** UI tests that do not depend on URL (`GroupScreen`, `HomeScreen`, modals).

### 3.2 `setupStoreAndWindow(options?)`

In addition to `initEmpty()`, defines `window.location` with defaults (`search: ""`, `href: "http://localhost/"`) and spies on `window.history.replaceState`.

**Use in:** tests that exercise `hydrateFromUrl` / `syncToUrl` — `app.store.test.ts` and `App.test.tsx`.

**Option `restoreMocks: true`:** calls `vi.restoreAllMocks()` before resetting state. Required in `app.store.test.ts` because the balance module is mocked with `vi.mock` and the spy needs to be restored between tests. The correct semantic order is: restore mocks → reset state.

```typescript
beforeEach(() => {
    setupStoreAndWindow({ restoreMocks: true });
});
```

## 4. Shared test data and inline factories

### 4.1 Test user constants

`tests/mocks/users.ts` exports `testAlice`, `testBob`, and `testUsers` — typed `User` objects with fixed IDs (`1` and `2`). Use these instead of defining inline user arrays in component tests that take user props directly.

```typescript
import { testUsers } from "@tests/mocks";

const users: User[] = testUsers;
```

### 4.2 Store setup helpers

| Helper | Location | Purpose |
|---|---|---|
| `setupTwoUsers()` | `tests/helpers/store-helpers.ts` | Adds Alice (id:1) and Bob (id:2) to the store |
| `setupGroupWithTwoMembers()` | `tests/helpers/store-helpers.ts` | Calls `setupTwoUsers()` + creates group "Trip" with both |
| `setupGroupWithNonMember()` | `tests/helpers/store-helpers.ts` | Calls `setupTwoUsers()` + adds Carol (id:3) + creates group with Alice and Bob only |

### 4.3 Inline factories

Do not use `beforeEach` to build state or render — use factories declared in the scope of the test file.

```typescript
import { setupGroupWithTwoMembers } from "@tests/helpers";

function setup(onClose = vi.fn()) {
    const group = setupGroupWithTwoMembers();
    const hook = renderHook(() => useExpenseForm(group.id, onClose));
    return { group, onClose, hook };
}

function renderScreen(groupId: number, onNavigate = vi.fn()) {
    return { onNavigate, ...render(<GroupScreen groupId={groupId} onNavigate={onNavigate} />) };
}

function renderModal() {
    render(<AddMemberModal groupId={group.id} />);
}
```

**Rule:** factories that appear in multiple test files go to `tests/helpers/`. Factories that appear in only one file stay local.

For components with multiple props that rarely change between tests, declare a `defaultProps` object at the top of the file and spread it into each render call:
```typescript
const defaultProps = {
    view: { screen: "home" as const },
    onNavigate: vi.fn(),
};

render(<Sidebar {...defaultProps} />);
render(<Sidebar {...defaultProps} view={{ screen: "group", groupId: 1 }} />);
```

**Rule:** use `defaultProps` when a component has 3 or more props and most tests only override one of them. Used in: `Sidebar.test.tsx`, `AppLayout.test.tsx`.

## 5. Mocking strategies

### 5.1 Dialog mock — centralized

`vi.mock("@components/ui/dialog", () => import("@tests/mocks/ui/dialog"))`

Used in: `AddMemberModal.test.tsx`, `AddGroupModal.test.tsx`, `AddUsersModal.test.tsx`, `ExpenseModal.test.tsx`, `SettlementModal.test.tsx`, `ExpensesSection.test.tsx`, `SettlementsSection.test.tsx`, `ConfirmDeleteDialog.test.tsx`.

Centralized because it is identical in all three files. Replaces the library’s headless component with a minimal implementation that: conditionally renders children, exposes a trigger button to open the dialog, and provides passthrough for header/title/footer.

### 5.2 Button mock — local in `AddMemberModal.test.tsx`

```typescript
vi.mock("@components/ui/button", () => ({
    Button: ({ onClick, disabled, children }: ButtonProps) => (
        <button onClick={onClick} aria-disabled={disabled}>{children}</button>
    ),
}));
```

Required because React Testing Library blocks `fireEvent.click` on buttons with native `disabled={true}`. The mock swaps `disabled` for `aria-disabled`, allowing the click to reach the handler and the guard clause to be exercised. No need for centralization — it only exists in one file.

### 5.3 Balance mock — `importOriginal` in `app.store.test.ts`

```typescript
vi.mock("@domain/balance", async (importOriginal) => {
    const actual = await importOriginal<typeof import("@domain/balance")>();
    return {
        ...actual,
        computeBalances: vi.fn(actual.computeBalances),
    };
});
```

Wraps `computeBalances` in a `vi.fn()` that, by default, delegates to the real implementation. Individual tests can override the return value to simulate edge cases (e.g., member without a balance entry). The `beforeEach` with `restoreMocks: true` restores the spy to the real implementation before each test.

### 5.4 Balance spy — `vi.spyOn` in `useGroupScreen.test.ts`

```typescript
import * as balanceDomain from "@domain/balance";
// inside the test:
vi.spyOn(balanceDomain, "computeBalances").mockReturnValueOnce([]);
```

Different from `app.store.test.ts`, `useGroupScreen.test.ts` uses `vi.spyOn` directly on the imported module. Suitable for small targeted tests that need to control the return value without affecting others.

## 6. Defensive guards

### 6.1 Convention

Tests that exist exclusively to cover defensive code branches — paths that TypeScript or business rules make unreachable via valid input — are grouped in:

```typescript
describe("defensive guards (unreachable in valid usage)", () => {
    test("...", () => { ... });
});
```

The label is inline documentation: any reader understands the block exists for coverage reasons, not because the path is accessible.

### 6.2 Placement

| File | Position of the describe |
|---|---|
| `compute-balances.test.ts` | L2 inside the top-level describe |
| `build-equal-expense.test.ts` | L2 inside the top-level describe |
| `build-fixed-expense.test.ts` | L2 inside the top-level describe |
| `build-percentage-expense.test.ts` | L2 inside the top-level describe |
| `app.store.test.ts` | L3 nested inside `describe("removeMemberFromGroup")` |
| `useGroupScreen.test.ts` | L2 inside the top-level describe |
| `useExpenseForm.test.ts` | L2 inside the top-level describe |
| `useSettlementForm.test.ts` | L2 inside the top-level describe |
| `computeCanSubmit.test.ts` | L2 inside the top-level describe |
| `getInitialExpenseState.test.ts` | L2 inside the top-level describe |
| `ExpensesSection.test.tsx` | L2 inside the top-level describe |
| `SettlementsSection.test.tsx` | L2 inside the top-level describe |
| `ExpenseModal.test.tsx` | L2 inside the top-level describe |
| `SettlementModal.test.tsx` | L2 inside the top-level describe |
| `MembersSection.test.tsx` | L2 inside the top-level describe |

**Rule:** defensive guards sit at L2 (or L3 when nested inside a behavior group). If the guard semantically belongs to an existing describe, nest it inside.

### 6.3 Tests that are NOT defensive guards

`handleOpenChange` tests in modals are valid behavioral tests — dialog closing is real functionality, not a defensive branch.

## 7. Type assertions on invalid data

To exercise branches that require invalid data unreachable via normal TypeScript:

```typescript
useAppStore.getState().addExpense(group.id, {
    splitMode: "unknown" as unknown as "equal",
    // ...
} as unknown as Omit<EqualExpense, "id">);
```

`as unknown as T` is the standard to force invalid types in guard tests. Do not use `@ts-ignore` — the double assertion documents intent more explicitly.

## 8. Answers to frequently asked questions

**Why `setupStoreOnly` instead of `setupStoreAndWindow` for UI tests?**
`GroupScreen`, `HomeScreen`, and modal tests do not exercise URL — they do not need mocked `window.location`. `setupStoreOnly` is simpler and better isolates what the test actually validates.

**Why doesn’t the dialog mock use `__mocks__`?**
The `__mocks__` directory with TypeScript and path aliases can be unpredictable in Vitest. The pattern `vi.mock("@components/ui/dialog", () => import("@tests/mocks/ui/dialog"))` with dynamic import is explicit and reliable.

**Why are Zod schemas excluded from coverage?**
`.schema.ts` files are shape declarations — they do not contain logic with branches. Zod validates at runtime, but there is no `if`/`else` to test.

**Why is `validGlobalEncoded` computed at import time?**
Computes `lzstring.compressToEncodedURIComponent(JSON.stringify(validGlobal))` when importing the module. Acceptable for tests — if `lz-string` has an initialization problem in the test environment, the error shows up immediately.
